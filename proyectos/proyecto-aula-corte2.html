2 Caso de estudio: portal de clientes de la Corporación Industrial del Caribe

Contexto

La Corporación Industrial del Caribe, el mismo cliente del primer corte, aprobó el documento de planificación de migración. Antes de migrar nada más, quiere ver funcionando el patrón de referencia para su portal de clientes: una web expuesta a Internet, una aplicación y una base de datos aisladas entre sí, y un servicio que siga respondiendo cuando falla una máquina o cuando sube la demanda.

"Quiero que el portal esté en la nube, pero que ni la aplicación ni mi base de datos sean visibles desde Internet. Y que si se cae un servidor o llega una campaña, el portal siga atendiendo a mis clientes sin que nadie tenga que intervenir."

Punto de partida: diseño inseguro heredado

El laboratorio entrega una VPC ya creada, con tres pares de subredes (públicas, privadas de aplicación y privadas de base de datos) distribuidas en dos zonas de disponibilidad. Sin embargo, la aplicación PHP está hoy en una sola instancia EC2 en una subred pública, y su sitio y su base MySQL corren juntos en esa misma máquina. Ese diseño tiene cuatro problemas que debes resolver:

  • Punto único de falla: si la instancia cae, el portal completo cae con ella.
  • Base de datos expuesta: la base vive en el mismo host que la web, accesible desde Internet.
  • Credenciales en el código: la contraseña de la base está escrita dentro de la aplicación.
  • Sin elasticidad: una sola máquina no absorbe picos de demanda ni se reemplaza sola.

Arquitectura de referencia por capas

3 Objetivo general

Transformar el portal de la Corporación, hoy una instancia única e insegura, en una arquitectura por capas: base de datos administrada, secretos fuera del código, aplicación en subredes privadas detrás de un balanceador y escalado automático. El resultado debe responder con datos reales de la base y seguir funcionando cuando falla un componente.

Principio del curso: los servicios de AWS son la plataforma; lo que se evalúa son los conceptos: segmentación, defensa por capas, base de datos administrada, gestión de secretos, alta disponibilidad y elasticidad. Si puedes explicar por qué cada recurso está donde está, el laboratorio está bien hecho.

4 Requisitos a cumplir (contenido mínimo)

La arquitectura final debe cumplir los siguientes requisitos. Cómo lograrlo es tu decisión técnica.

  1. Base de datos MySQL administrada (RDS) ubicada en las subredes de base de datos, sin acceso público, y que solo acepte conexiones desde la capa de aplicación.
  2. Credenciales en un gestor de secretos. Ni el código de la aplicación ni la plantilla de lanzamiento pueden contener la contraseña en texto plano.
  3. Datos importados desde el volcado SQL que entrega el laboratorio, cargados en la base administrada.
  4. Servidores de aplicación en subredes privadas, sin IP pública. El acceso SSH queda restringido a administradores, nunca abierto a todo Internet.
  5. Acceso web anónimo solo a través de un balanceador de carga de aplicaciones desplegado en subredes públicas de al menos dos zonas de disponibilidad.
  6. Escalado automático con un grupo de Auto Scaling, una plantilla de lanzamiento y una política de seguimiento de objetivo.
  7. Página de consulta funcionando: la aplicación devuelve datos de la base cuando se accede por el DNS del balanceador.
Si la página de consulta no responde, revisa en este orden: grupo de seguridad de la base, conexión desde la aplicación, secreto y, por último, el balanceador.
