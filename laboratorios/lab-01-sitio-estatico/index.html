1. Qué vas a aprender

En este laboratorio usarás el almacenamiento de objetos de la nube como si fuera Amazon S3:

  • crear un bucket y comprobar su región;
  • activar versionado y demostrar dos versiones de un objeto;
  • publicar un sitio estático con los tipos MIME correctos;
  • comprobar el sitio por HTTP en la terminal y en la pestaña Sitio web;
  • distinguir qué hace S3 real y qué no emula la nube de la estación.

No necesitas tarjeta de crédito, cuenta de AWS ni conexión a Internet. La nube vive dentro de tu estación, en http://127.0.0.1:4566.

3. Antes de empezar

Comprueba que la nube responde y que todavía no hay buckets:

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4566/
aws s3 ls

La primera orden debe imprimir 200 (o 404, según la versión de floci: lo importante es que algo responda). La segunda no debe listar nada: tu nube empieza vacía.

Si aws dice «Unable to locate credentials»: ejecuta source /etc/profile.d/lab-aws.sh y vuelve a probar. El wrapper aws ya añade --endpoint-url; no hace falta escribirlo en cada comando.

4. Paso 1 — Crear el bucket

aws s3api create-bucket --bucket sitio-hep
aws s3api head-bucket --bucket sitio-hep && echo "bucket OK"
aws s3api get-bucket-location --bucket sitio-hep

us-east-1 es la región por defecto y no necesita LocationConstraint (en otras regiones sí). La respuesta de get-bucket-location puede traer LocationConstraint: null: significa «us-east-1».

Criterio 1 El bucket sitio-hep existe en us-east-1.

5. Paso 2 — Activar versionado

aws s3api put-bucket-versioning \
  --bucket sitio-hep \
  --versioning-configuration Status=Enabled

aws s3api get-bucket-versioning --bucket sitio-hep

Debe responder "Status": "Enabled". El versionado guarda cada subida de un objeto; no se activa solo y no se puede «simular» subiendo dos archivos con nombres distintos.

Criterio 2 Versionado Enabled y index.html con al menos dos versiones.

6. Paso 3 — Publicar los objetos con su Content-Type

S3 guarda el tipo MIME en el momento de la subida, como metadato del objeto. Que el archivo se llame .css no basta: hay que declararlo. Usa s3api put-object para no depender de lo que adivine la CLI:

cd ~/sitio

aws s3api put-object --bucket sitio-hep --key index.html \
  --body index.html --content-type "text/html; charset=utf-8"

aws s3api put-object --bucket sitio-hep --key error.html \
  --body error.html --content-type "text/html; charset=utf-8"

aws s3api put-object --bucket sitio-hep --key estilo.css \
  --body estilo.css --content-type "text/css; charset=utf-8"

Comprueba los metadatos:

aws s3api head-object --bucket sitio-hep --key index.html
aws s3api head-object --bucket sitio-hep --key estilo.css

Criterio 3 Los tres objetos existen y su ContentType es text/html… para los HTML y text/css… para el CSS.

7. Paso 4 — Segunda versión de index.html

El versionado se demuestra con dos subidas distintas del mismo objeto. Edita ~/sitio/index.html, busca la línea:

Versión del sitio: <strong>borrador</strong>.

y cámbiala por algo como:

Versión del sitio: <strong>1.0 — publicada</strong>.

Vuelve a subir el archivo:

aws s3api put-object --bucket sitio-hep --key index.html \
  --body index.html --content-type "text/html; charset=utf-8"

Y lista las versiones:

aws s3api list-object-versions --bucket sitio-hep --prefix index.html

Deben aparecer dos entradas en Versions para la clave index.html, con VersionId distintos y la más reciente marcada como "IsLatest": true.

Criterio 2 (completo) Versionado activo y dos versiones del index.

8. Paso 5 — Configurar el sitio web

En S3 real, el «website hosting» se configura en el bucket con un documento de índice y uno de error. Hazlo también aquí:

aws s3api put-bucket-website --bucket sitio-hep \
  --website-configuration '{
    "IndexDocument": {"Suffix": "index.html"},
    "ErrorDocument": {"Key": "error.html"}
  }'

aws s3api get-bucket-website --bucket sitio-hep

Una limitación que debes conocer (y explicar)

La nube de la estación guarda la configuración del sitio, pero no la aplica al servir:

  • GET /sitio-hep/ devuelve el listado XML del bucket, no index.html;
  • una clave inexistente devuelve un XML de error de S3, no tu error.html.

Por eso el laboratorio comprueba las URLs directas de los objetos:

http://127.0.0.1:4566/sitio-hep/index.html
http://127.0.0.1:4566/sitio-hep/error.html
Esto es una diferencia entre el emulador y AWS real. En AWS real, con IndexDocument y ErrorDocument, el sitio resolvería / y los 404 con tus páginas. En la entrega explica en una frase qué cambiaría en AWS real.

9. Paso 6 — Comprobar el sitio

curl -i http://127.0.0.1:4566/sitio-hep/index.html
curl -i http://127.0.0.1:4566/sitio-hep/error.html
curl -i http://127.0.0.1:4566/sitio-hep/estilo.css
  • index.html → 200 OK, Content-Type: text/html…, cuerpo con CaribeMart HEP.
  • error.html → 200 OK, cuerpo con No encontrado.
  • estilo.css → 200 OK, Content-Type: text/css….

En la pestaña Sitio web de la plataforma verás el mismo sitio a través del proxy de la sesión (http://127.0.0.1:8080/); el proxy traduce / a index.html.

Y el autocontrol:

revisar

Debe terminar con 5 de 5 criterios en verde. Si falta alguno, el detalle te dice exactamente qué corregir.

12. Para ir más allá (opcional, no se califica)

  • Añade una bucket policy que permita s3:GetObject solo a index.html y error.html (aws s3api put-bucket-policy).
  • Crea una regla de ciclo de vida que expire versiones antiguas (put-bucket-lifecycle-configuration).
  • Sube un cuarto objeto aviso.txt y comprueba que Content-Type: text/plain también se guarda.
  • Compara s3 cp con s3api put-object: ¿en qué caso se adivina el MIME y en cuál lo declaras tú?
