IA = inteligencia artificial
Paradigma computacional

Del software determinista al probabilístico

Reglas escritas a mano frente a probabilidades aprendidas
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: AWS Well-Architected, Generative AI Lens (docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens) 2 / 15
IF = condición «si» · ELSE = alternativa «si no»
Para diseñar infraestructura de IA primero hay que entender qué cambió respecto al software que ya conocemos. Arriba vemos el código tradicional: una entrada pasa por reglas IF y ELSE escritas por un programador y produce una sola salida; si repetimos la entrada, obtenemos exactamente lo mismo. Abajo está el modelo de lenguaje. La misma entrada atraviesa los pesos del modelo, que son millones de números aprendidos de ejemplos, y en lugar de una respuesta fija el modelo calcula probabilidades para la próxima palabra. Luego una palabra se sortea según esas probabilidades. Por eso la misma pregunta puede producir respuestas distintas. Para quien diseña la nube esto cambia el trabajo: ya no optimizamos reglas, sino la memoria y la velocidad con que se leen esos pesos, y además debemos medir la calidad de las respuestas, no solo si el servicio respondió.
Arquitectura del modelo

Un modelo de lenguaje por dentro

Del texto de entrada al token de salida
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: Amazon Bedrock User Guide, Models at a glance (docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html) 3 / 15
GPU = unidad de procesamiento gráfico · API = interfaz de programación
Veamos un modelo de lenguaje como una tubería de seis estaciones, sin entrar en matemáticas. Entra un texto, por ejemplo tu pregunta. Primero se parte en tokens, que son trozos de palabras. Cada token se convierte en un vector, es decir, una lista de números que representa su significado. Esos números atraviesan decenas de capas que combinan el contexto: aquí vive casi todo el cálculo. A la salida el modelo asigna una probabilidad a cada posible token siguiente, y se elige uno. Observen la flecha roja: ese camino completo se repite por cada token de la respuesta. Y la idea que nos importa: un modelo es simplemente un archivo enorme de pesos más un programa que lo ejecuta. Para la nube, eso significa mover y mantener en memoria ese archivo cada vez que alguien hace una pregunta.
Generación autorregresiva

Un token a la vez

El modelo no escribe la respuesta de golpe
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: Amazon Bedrock User Guide, Inference parameters (docs.aws.amazon.com/bedrock/latest/userguide/inference-parameters.html) 4 / 15
Este es el mecanismo más importante de toda la clase. A la izquierda está el contexto actual: imaginemos que el texto es "La nube es". El modelo, en el centro, hace una pasada completa y entrega un solo token nuevo, aquí la palabra "flexible". Ese token no se muestra y se olvida: se agrega al contexto, y el ciclo vuelve a empezar con "La nube es flexible" para producir el siguiente. Lo ven en la flecha roja que regresa. El proceso termina cuando el modelo emite una señal de fin o llega al límite de longitud que configuramos. La consecuencia para la arquitectura es directa: una respuesta larga significa muchas pasadas, y cada pasada necesita leer los pesos desde la memoria. Por eso el tiempo de respuesta crece con la longitud de la salida, y por eso conviene mostrar el texto en streaming a medida que se genera.
Distribución de probabilidad

Cada paso es una apuesta ponderada

El modelo reparte 100 % entre las palabras posibles
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: Amazon Bedrock User Guide, Inference parameters (consulta 2026-11-05); valores ilustrativos 5 / 15
Aquí vemos qué pasa dentro del modelo justo antes de escribir la siguiente palabra. Para el texto "La nube es", el modelo no tiene una única respuesta: reparte el cien por ciento de probabilidad entre las palabras posibles. En este ejemplo ilustrativo, "flexible" recibe cincuenta y cinco por ciento, "escalable" veinticinco, "costosa" doce y cualquier otra palabra el resto. Los valores son inventados para enseñar la idea; en un modelo real hay miles de candidatos. Luego el sistema sortea una palabra siguiendo esos pesos, como una ruleta con sectores desiguales. La palabra más probable sale más veces, pero no siempre. Esto explica por qué un modelo puede responder distinto ante la misma pregunta, y nos lleva a la pregunta práctica de esta clase: qué parámetros del servicio nos permiten controlar ese sorteo para que sea más estable o más creativo.
Control del muestreo

Temperatura: afila o aplana la curva

Un solo parámetro cambia el carácter de la respuesta
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: Amazon Bedrock User Guide, Inference parameters (docs.aws.amazon.com/bedrock/latest/userguide/inference-parameters.html) 6 / 15
SQL = lenguaje de consulta estructurado
La temperatura es el primer control que expone la API. Miren los tres paneles: cada uno muestra las probabilidades de cuatro palabras candidatas. Con temperatura baja, a la izquierda, una barra domina y las demás casi desaparecen: el modelo elige casi siempre lo mismo, ideal para generar SQL o extraer datos de una factura, donde queremos resultados repetibles. Con temperatura media, al centro, hay variedad moderada, apropiada para un chat de atención al cliente que debe sonar natural. Con temperatura alta, a la derecha, las barras se igualan y aparecen palabras raras: sirve para lluvia de ideas, pero aumenta el riesgo de errores. En Amazon Bedrock el parámetro se llama temperature. Como diseñadores no lo dejamos al azar: lo fijamos por caso de uso y lo documentamos junto con el prompt.
Control del muestreo

Top-K y Top-P: dónde cortar la lista

Dos formas de descartar candidatos improbables
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: Amazon Bedrock User Guide, Inference parameters (consulta 2026-11-05); valores ilustrativos 7 / 15
Además de la temperatura, la API permite recortar la lista de candidatos antes del sorteo. En el gráfico tenemos seis palabras ordenadas de la más a la menos probable, con valores ilustrativos. Top-K corta por cantidad: si fijamos K igual a tres, solo A, B y C participan, sin importar cuánta probabilidad sumen. Top-P corta por probabilidad acumulada: sumamos desde la más probable, cuarenta, sesenta y cinco, ochenta, noventa, y nos detenemos al alcanzar el umbral del noventa por ciento, así que entran A, B, C y D. La ventaja de Top-P es que se adapta: si el modelo está muy seguro entrega pocos candidatos, y si duda entrega más. En ambos casos las palabras fuera del corte nunca se sortean. Para el diseño, recuerden la regla práctica: ajuste uno de los controles a la vez y mida el resultado.
Dos mundos de cómputo

Entrenar un modelo frente a servirlo

Para la mayoría de equipos el reto es servir
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: AWS Well-Architected, Generative AI Lens (docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens) 8 / 15
GPU = unidad de procesamiento gráfico
Hay dos actividades que se confunden con frecuencia. Arriba está el entrenamiento: un clúster grande de servidores con muchas GPU trabaja unido durante un proyecto finito y produce un archivo de pesos, el modelo ya aprendido. Eso lo hacen pocas organizaciones. Abajo está la inferencia, que es lo que ustedes van a diseñar: usuarios envían peticiones, un servidor con GPU lee esos pesos y devuelve la respuesta token a token. Esa operación se repite todos los días, a toda hora, y se paga de forma continua. Fíjense en la flecha punteada: los pesos se copian al servidor de inferencia, no se vuelven a entrenar. Para un equipo de una empresa mediana en Barranquilla, casi nunca se justifica entrenar desde cero; lo habitual es consumir un modelo ya entrenado y concentrarse en servirlo bien, con la latencia, el costo y la seguridad que el negocio exige.

Los pesos ocupan la memoria primero

Lo que sobra atiende a los usuarios
Arquitectura en la Nube · Semana 14 · Parte 1 de 4 Fuente: aws.amazon.com/ec2/instance-types/g5/ (24 GB por GPU A10G); NVIDIA, Deep Learning Performance (2 bytes por parámetro en FP16); cálculo propio 9 / 15
GPU = unidad de procesamiento gráfico · GB = gigabyte · VRAM = memoria de la GPU
Pensemos la memoria de la tarjeta gráfica como una caja de veinticuatro gigabytes, que es la capacidad de una instancia g5.xlarge según la lista de precios oficial de AWS. Lo primero que entra son los pesos del modelo. Si el modelo tiene ocho mil millones de parámetros y cada uno se guarda en dos bytes, o sea dieciséis bits, los pesos ocupan dieciséis gigabytes, el bloque rojo. Quedan ocho gigabytes libres, el bloque azul. Y ahí es donde se aloja el contexto de cada usuario que está conversando: mientras más usuarios simultáneos y más largas las conversaciones, menos memoria libre. Esa es la razón por la que la memoria, y no la potencia de cálculo, suele decidir cuántas personas puede atender un servidor. Es un cálculo propio, una regla práctica de dimensionamiento que usaremos varias veces en esta clase.

Fundamento léxico

De caracteres a subpalabras (tokens)

Cómo el texto se convierte en identificadores numéricos
Arquitectura en la Nube · Semana 14 · Parte 2 de 4 Fuente: Sennrich et al. (2016), arXiv:1508.07909 (codificación por pares de bytes) 2 / 15
ID = identificador
El modelo no lee palabras enteras ni letras sueltas: lee tokens. En este diagrama observamos el flujo de conversión con la palabra descentralización. Primero, el algoritmo de tokenización descompone la cadena en subpalabras frecuentes aprendidas durante su entrenamiento previo: el prefijo des, la raíz central, el sufijo verbal iza y la terminación ción. Cada una de estas unidades conforma un token independiente. Segundo, cada token se mapea directamente a un número entero único dentro de la tabla del vocabulario, transformando el texto en una secuencia numérica compacta. En términos de arquitectura en la nube, esta relación define el volumen de datos que atraviesa los aceleradores: en promedio, un token equivale a cuatro caracteres en inglés, pero en español suele requerir más fragmentos debido a la morfología y acentuación.
Mecanismo de tokenización

Byte-Pair Encoding (BPE)

Fusión de pares frecuentes hasta alcanzar el vocabulario
Arquitectura en la Nube · Semana 14 · Parte 2 de 4 Fuente: Sennrich et al. (2016), arXiv:1508.07909 3 / 15
El estándar de la industria para segmentar texto es Byte-Pair Encoding o BPE. El diagrama muestra su mecanismo paso a paso. En el nivel inicial, el texto se representa como caracteres individuales aislados. En cada iteración estadística, el algoritmo identifica el par de símbolos adyacentes más repetido en el corpus y lo fusiona en una nueva unidad léxica compuesta. En nuestro ejemplo, el par a-s se consolida primero, seguido por la raíz c-a-s, hasta que la palabra se codifica en solo dos tokens. Este método ofrece una ventaja crítica para la nube: al descender a nivel de bytes cuando encuentra términos raros, elimina por completo el error de palabra desconocida o token fuera de vocabulario, permitiendo procesar cualquier jerga técnica o lenguaje de programación sin fallos estructurales.
Disparidad lingüística

El impuesto de tokenización en español

Un aspecto financiero y operativo clave que los ingenieros y arquitectos en Colombia deben dominar con rigor es el sobrecosto derivado de la tokenización en idiomas romances. Observemos la comparativa directa en pantalla: la instrucción para crear una red privada en inglés requiere exactamente cuatro tokens limpios. Evolución de vocabularios

Menos fragmentación, capa de salida más grande

Menos fragmentación a costa de una capa de salida más grande
Arquitectura en la Nube · Semana 14 · Parte 2 de 4 Fuente: Meta, model cards de Llama 2 y Llama 3 (llama.meta.com) 5 / 15
VRAM = memoria de la GPU
El tamaño del vocabulario de un modelo representa un compromiso directo de arquitectura. Los modelos de primera generación empleaban vocabularios de apenas treinta y dos mil tokens, fragmentando excesivamente el español y el código fuente. En la actualidad, modelos como Claude 5.5 y GPT-6 integran catálogos superiores a doscientos mil tokens, logrando que palabras completas en español se procesen como un único token. No obstante, existe una contrapartida física en la GPU: la matriz final de proyección o LM Head debe calcular probabilidades sobre doscientos mil elementos en cada paso, demandando más memoria VRAM y mayor ancho de banda solo para almacenar la capa de salida. Conocer este balance permite justificar por qué los modelos pequeños aún prefieren vocabularios intermedios de ciento veintiocho mil tokens.

La ventana de contexto representa el espacio total de memoria de trabajo que el modelo puede observar de manera simultánea en una sola invocación. En el diagrama superior vemos su distribución operativa: las instrucciones base y documentos del prompt de sistema, el historial acumulado de turnos de diálogo previos y el margen expresamente reservado para la generación de salida mediante el parámetro max_tokens. Evolución temporal

De 2.048 a 200.000 tokens de contexto

Un salto de casi cien veces en cuatro años
Arquitectura en la Nube · Semana 14 · Parte 2 de 4 Fuente: Brown et al. (2020), arXiv:2005.14165 (GPT-3); Anthropic, documentación de modelos (Claude 3.5 Sonnet) 7 / 15
GPT = transformador generativo preentrenado
La capacidad de contexto ha experimentado una expansión exponencial en solo seis años. En 2020, los modelos estaban restringidos a dos mil tokens, obligando a fragmentar cualquier texto largo en pedazos minúsculos. Hacia 2024, la barrera subió a doscientos mil tokens, y en 2026 arquitecturas como Claude 5.5 y Nova procesan rutinariamente entre uno y dos millones de tokens en una sola llamada. Esto revoluciona la nube: ahora podemos volcar manuales de usuario completos o bases de datos sin necesidad inmediata de bases vectoriales complejas. Sin embargo, no olviden el desafío técnico: a mayor contexto, mayor costo por llamada y mayor probabilidad de que el modelo sufra el fenómeno de la aguja en el pajar si no estructuramos bien el prompt.
Mecánica de memoria

Por qué el contexto largo gasta memoria

Por qué el contexto largo consume memoria de la GPU
Arquitectura en la Nube · Semana 14 · Parte 2 de 4 Fuente: Dao et al. (2022), FlashAttention (arXiv:2205.14135) 8 / 15
KV = clave-valor (caché de atención) · GPU = unidad de procesamiento gráfico
El cuello de botella de los modelos de atención es su naturaleza cuadrática: cada token de la secuencia debe calcular su afinidad con todos los demás tokens previos. En secuencias de cien mil tokens, esto representaría diez mil millones de operaciones. Para hacer viable la inferencia en producción, los motores implementan el KV Cache: calculan los vectores Key y Value de cada token una sola vez y los almacenan en la memoria VRAM del acelerador. Así, el siguiente token solo calcula su producto contra los datos en caché. La lección de arquitectura es crucial: el KV Cache ahorra cómputo pero consume memoria viva en la GPU; en documentos muy extensos, la memoria ocupada por la conversación puede superar el tamaño del propio modelo.

Para diagnosticar el rendimiento de un clúster hay que separar conceptualmente las dos etapas de una petición. La fase de prefill procesa todo el texto de entrada al unísono: es una operación limitada por cómputo que aprovecha al máximo los núcleos Tensor para calcular los embeddings y el KV inicial. El tiempo que tarda esta etapa determina la métrica TTFT o espera hasta el primer token. Acto seguido comienza la fase de decode, que emite un token por iteración: aquí el cómputo aritmético es bajo pero el tráfico de memoria es colosal, pues cada token exige releer todos los parámetros y la caché acumulada. Por ello, las arquitecturas más avanzadas en la nube comienzan a separar físicamente los servidores que atienden prefill de aquellos dedicados a decode para evitar interferencias mutuas.

Árbol de decisión: tres caminos

Un árbol de decisión entre API gestionada, servidor propio y local

EC2 = cómputo elástico de Amazon · GPU = unidad de procesamiento gráfico · API = interfaz de programación
Frente a un nuevo requerimiento de inteligencia artificial, el arquitecto debe evaluar tres caminos posibles mediante un árbol de decisión disciplinado. La primera pregunta es regulatoria: ¿los datos son estrictamente confidenciales y la ley prohíbe su salida hacia centros de datos de terceros? Si la respuesta es afirmativa, el camino obligatorio es la inferencia local con herramientas como Ollama sobre servidores propios. Si la nube está permitida, la siguiente pregunta es económica: ¿el volumen de consultas es masivo y predecible las veinticuatro horas del día? Si es así, operar instancias dedicadas con GPU como g5.xlarge en Amazon EC2 ofrece un costo marginal menor. Para la gran mayoría de casos corporativos con tráfico fluctuante, el camino natural es una API gestionada serverless como Amazon Bedrock, donde solo se pagan los tokens reales consumidos sin asumir la complejidad de operar hardware acelerado.

Operar servidores acelerados dedicados es una decisión puramente económica y operativa. Las ventajas son indiscutibles cuando el sistema está plenamente cargado: el costo por token adicional es prácticamente cero porque la máquina ya está encendida, nadie puede bloquear el tráfico mediante cuotas externas de terceros y la organización posee total libertad sobre el software sin temer que un proveedor declare el modelo en estado de fin de vida. Por el contrario, los contras son muy severos: asumir una tarifa fija de setecientos treinta y cuatro dólares mensuales por nodo base, gestionar parches complejos de Linux y controladores NVIDIA, y enfrentar arranques en frío de varios minutos al intentar autoescalar. La recomendación es tajante: solo adquieran servidores dedicados cuando los cálculos matemáticos demuestren que el volumen satura la capacidad contratada.

El tercer arquetipo es la inferencia puramente local, ejecutada dentro del perímetro físico de la organización sin tocar la nube. Herramientas modernas como Ollama empaquetan motores altamente eficientes escritos en C++ que permiten correr modelos fundacionales sobre servidores on-premise, estaciones de trabajo o portátiles con GPUs estándar. Mediante el formato binario GGUF, los modelos se cuantizan en cuatro u ocho bits para ejecutarse consumiendo poca memoria RAM o VRAM, exponiendo un puerto local once mil cuatrocientos treinta y cuatro con una API REST idéntica a los estándares del sector. Este diseño ofrece la máxima garantía de soberanía técnica: ni una sola palabra, registro bancario o historia clínica abandona el edificio, cumpliendo de forma impecable las normativas más estrictas a cambio de una capacidad de procesamiento restringida a modelos pequeños o medianos.
Marco regulatorio

Soberanía del dato y regulación en Colombia

Cumplimiento de la Ley 1581 de 2012 en IA
Arquitectura en la Nube · Semana 14 · Parte 4 de 4 Fuente: Ley 1581 de 2012, art. 26 (Gestor Normativo, Función Pública); Superintendencia de Industria y Comercio 8 / 15
AWS = Amazon Web Services · IA = inteligencia artificial
El diseño de sistemas con inteligencia artificial en Colombia no es un ejercicio puramente técnico: está enmarcado estrictamente en la Ley 1581 de 2012 sobre protección de datos personales. El Artículo 26 prohíbe de forma explícita la transferencia transfronteriza de información confidencial a países que no garanticen niveles adecuados de protección. Afortunadamente, la Superintendencia de Industria y Comercio reconoce que regiones en Estados Unidos, como Virginia, y en la Unión Europea cumplen con estos estándares, habilitando el uso de centros de datos de proveedores como AWS. No obstante, el principio de confidencialidad obliga a garantizar contractualmente que ningún dato del cliente se utilice para reentrenar modelos base del proveedor, exigiendo que las aplicaciones cuenten con el consentimiento previo y expreso de los ciudadanos para el tratamiento algorítmico de su información.

Arquitectura híbrida: el enrutador inteligente

Clasificar la consulta antes de elegir el modelo
Arquitectura en la Nube · Semana 14 · Parte 4 de 4 Fuente: AWS Generative AI Lens (Architecture Patterns: model routing and cascading) 10 / 15
FAQ = preguntas frecuentes
El patrón más sofisticado y rentable en producción es la arquitectura híbrida con enrutador inteligente. En lugar de atar rígidamente todo el sistema a un solo modelo, interponemos un clasificador ligero en la entrada: un microservicio ultra-rápido o un modelo muy económico como Nova Micro que analiza la intención y complejidad de la consulta en menos de veinte milisegundos. Si la tarea es cotidiana, como responder preguntas frecuentes o resumir un texto estándar, la desvía hacia modelos ligeros como Nova Lite o Haiku 5.5. Únicamente cuando detecta razonamiento matemático intrincado, análisis de código o resolución de disputas legales, escala la llamada hacia Claude Sonnet 5.5. Este esquema garantiza que el usuario perciba la máxima excelencia del sistema reduciendo a la vez más del sesenta por ciento del gasto operativo mensual.

Finalmente, el modelo procesa el cálculo y todas las interacciones se registran de forma inmutable en un bucket S3 cifrado con claves KMS del cliente, asegurando trazabilidad completa exigible en auditorías de seguridad y cumplimiento normativo.
Ciberseguridad en IA

Defensas contra el riesgo número uno

Defensas arquitectónicas contra el riesgo número uno de OWASP
Arquitectura en la Nube · Semana 14 · Parte 4 de 4 Fuente: OWASP Top 10 para aplicaciones con LLM 2025 (LLM01); AWS Bedrock Guardrails 12 / 15
PDF = formato de documento portátil · RAG = generación aumentada por recuperación · LLM = modelo de lenguaje de gran tamaño · IA = inteligencia artificial · OWASP = Proyecto Abierto de Seguridad de Aplicaciones Web
La vulnerabilidad número uno identificada por el estándar internacional de OWASP para aplicaciones con modelos de lenguaje es la inyección de prompts. Ocurre cuando un atacante incrusta instrucciones maliciosas diseñadas para suplantar las directrices originales del sistema, logrando que el modelo filtre información secreta o ejecute herramientas no autorizadas. Esta amenaza puede ser directa a través de la interfaz de chat, o indirecta cuando el modelo lee un archivo PDF o correo manipulado. Como arquitectos, debemos entender que esta falla no se remedia pidiéndole amablemente al modelo que sea seguro en el prompt; se resuelve con barreras externas de ingeniería: activando filtros dedicados de Guardrails, delimitando con etiquetas XML las variables de entrada, restringiendo los permisos de las APIs con mínimo privilegio y exigiendo validación humana para acciones críticas.
